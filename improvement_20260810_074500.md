## 3. run_budget merge-on-resume fix (real bug)

**Symptom:** `logs/run_budget_<id>.json` undercounted visuals/LLM spend on resumed
runs. Observed: ledger showed 6 visuals even though 15 images were generated across
this topic's multiple resume attempts.

**Root cause:** `src/engine/run_budget.py:start()` is invoked on every
`run_pipeline()` call (`orchestrator.py:147`). It unconditionally **reset** all
counters to zero. When a pipeline **resumed** from a checkpoint, the per-run file
was overwritten with only the post-resume session's spend, clobbering the prior
tally. Real cost tracking was therefore wrong-low for any run that needed a resume
(which the auto-resume in `run_production.sh` triggers whenever a run doesn't reach
`PUBLISHED_SUCCESS`).

**Fix:** `start()` now calls `_load_prior()`, which reads any existing
`run_budget_<id>.json` and re-seeds `_usd/_yt/_calls/_notes` so a resumed session
**accumulates** on top of the prior tally instead of resetting. Fresh runs (no prior
record) still start from zero. Verified: session1 (1 visual, 1 llm) → resume session
(+2 visuals) persists `visuals.calls=3`, `llm.calls=1`. All 8 hermetic tests pass.

**Note:** `media_budget.json` (the paid-spend authority) was always correct — this
fix aligns the diagnostic `run_budget` ledger with it.

## 4. Visual cache key: fold in shot_id (fixes intra-video collision)

**Issue:** the visual cache key was `sha256(visual_prompt)` where `visual_prompt` is
the enriched prompt. The comment claimed it included "act + shot id", but `shot_id`
was NOT actually part of the key — only the raw prompt + act tone were. Two
**different** shots in the same video sharing a prompt+act therefore produced the
**same** key, so the 2nd shot would HIT and reuse the 1st shot's image →
duplicate-looking visuals within a single video.

**Fix (media_producer.py):** both the HIT-check and STORE key now prefix the shot id —
`_visual_cache_key(f"{shot.shot_id}:{visual_prompt}")`. Verified semantics:
- Same shot re-rendered (proofing, narration-fix, resume) → identical key → **valid cross-run reuse preserved**
- Different shot, same prompt → different key → **collision resolved**

All 8 hermetic tests pass.

## 5. LLM result cache — recommended NOT to add

Reviewed whether an LLM result cache is safe here; conclusion is **not**:
1. **Staleness** — cached scripts would freeze outdated news/facts/date context into videos; the whole `--resume`/auto-resume flow re-runs the LLM intentionally to stay current.
2. **Breaks the revision loop** — a prompt-hash cache would return the same violating draft, so the Observer repair loop would never converge (re-serves cached bad output).
3. **Rare hits** — generation/polish/repair prompts embed topic + date + fact corpus + per-shot violations, so exact-match hits would be vanishingly rare (low value, added complexity).
4. **Cache poisoning** — a bad/truncated response cached would propagate to every identical call.

The **RAG cache** (6h TTL, `rag_retriever.py`) already covers the expensive retrieval
half; generation should run fresh. If ever added, it must be env-opted-in, keyed on
`route + prompt hash + model`, TTL-bounded, and never enabled on generate/polish/repair/critic routes.
